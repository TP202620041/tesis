## Payload que recibe el Service Worker
El evento `push` trae un JSON en UTF-8 (`event.data.json()`):

```json
{
  "titulo": "ViaSegura: su reporte esta en proceso",
  "cuerpo": "Su reporte #42 esta en proceso.",
  "url": "/mis-reportes/42",
  "reporteId": 42,
  "estado": "EN_PROCESO"
}
```

| Campo | Tipo | Notas |
|---|---|---|
| `titulo` | string | Título de la notificación. |
| `cuerpo` | string | Texto corto, con el estado en palabras («esta en proceso», «fue resuelto»…). No lleva el comentario del municipio (ese va en el correo y en el detalle). |
| `url` | string | Ruta relativa de la PWA a abrir en `notificationclick`. |
| `reporteId` | number | Reporte del propio usuario. |
| `estado` | string | Valor técnico: `RECIBIDO` \| `EN_PROCESO` \| `RESUELTO` \| `RECHAZADO`. Para lógica, no para mostrar. |

Sugerencia para el SW: `self.registration.showNotification(titulo, { body: cuerpo, data: { url }, tag: 'reporte-' + reporteId })` y, en `notificationclick`, `clients.openWindow(event.notification.data.url)` (o enfocar una pestaña abierta). El `tag` coincide con el tópico del backend: un aviso nuevo del mismo reporte reemplaza al anterior.

TTL: 24 h. Un aviso que no llega a entregarse en ese plazo se descarta.

## Flujo de suscripción
1. Consentimiento `NOTIFICACIONES_PUSH` (`POST /api/auth/me/consentimientos`).
2. `GET /api/notificaciones/vapid-public-key`. Si da 404, no ofrecer push.
3. `Notification.requestPermission()` y `registration.pushManager.subscribe({ userVisibleOnly: true, applicationServerKey: <clavePublica decodificada de base64url a Uint8Array> })`.
4. `POST /api/notificaciones/suscripciones` con `subscription.toJSON()` + `userAgent`.

Repetir el paso 4 en cada inicio de sesión si el navegador ya tiene una suscripción: reasigna el navegador al usuario actual y reactiva una suscripción que el backend haya marcado inactiva.

## Al cerrar sesión
- Antes de borrar el token: `DELETE /api/notificaciones/suscripciones` con `{ endpoint }` de este navegador (sigue permitido aunque falten los términos). Así este navegador deja de recibir los avisos de ese usuario.
- Opcional: `subscription.unsubscribe()` si no se quiere conservar la suscripción para el próximo usuario. Si se conserva, el siguiente login la vuelve a registrar (paso 4).
- Para desactivar push en **todos** los dispositivos: `DELETE /api/auth/me/consentimientos/NOTIFICACIONES_PUSH`.

## Notas para el frontend
- Si el servicio de push del navegador responde 404/410 (la suscripción caducó), el backend la marca inactiva y no vuelve a intentar hasta que el navegador la registre otra vez.
- Si el push falla, el aviso cae a correo solo si el usuario tiene `NOTIFICACIONES_CORREO`.
- Con preferencia `AMBAS` llegan push **y** correo; con `PUSH`, solo push (y correo solo si el push falla).
- **Rotación de claves VAPID:** tras rotarlas, el servicio de push responde 401/403 a las suscripciones viejas y fallan (el aviso cae a correo si hay permiso) hasta que el navegador se vuelve a suscribir. El backend **no** las desactiva por un 401/403 (no lo distingue de un error de configuración propio). Por eso, al iniciar sesión el frontend debe comparar `subscription.options.applicationServerKey` con la clave de `GET /api/notificaciones/vapid-public-key` y, si difieren, hacer `unsubscribe()`, `subscribe()` con la nueva y volver a hacer el `POST` de la suscripción.
- Los avisos se envían de forma asíncrona tras el cambio de estado: pueden llegar unos segundos después de que el funcionario guarde.
- `npm run api:sync` generará `ClavePublicaVapidResponse`.
